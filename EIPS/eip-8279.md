## Abstract

Meter the bytes each opcode adds to the [EIP-7928](./eip-7928.md) Block Access List in an explicit per-transaction counter, and fold that count, at 64 gas/byte, into the transaction's floor, checked at runtime before the BAL grows. The count is a strict upper bound on the transaction's BAL bytes: it is never refunded or rewound. Under [EIP-7976](./eip-7976.md) and EIP-7928 an attacker can pack ~1.55 MiB into a 60M-gas block: 75% of gas on cold `SLOAD`s (32 BAL bytes per 2,100 gas) + 25% on calldata at 16 gas/byte. On top of [EIP-8131](./eip-8131.md)'s tx-content floor (same rate), block content is capped at `block_gas_limit / 64 ≈ 0.89 MiB`, a ~42% cut in worst-case block size at an unchanged gas limit. Neither EIP alone closes the bypass: 8131 does not price BAL bytes; 8279 reuses 8131's floor. Typical transactions are unaffected; the floor binds on its own only for skipped [EIP-7702](./eip-7702.md) authorizations and, once [EIP-8037](./eip-8037.md) moves the code deposit into state gas, for the code a deployment writes (see [Backwards Compatibility](#backwards-compatibility)).

## Motivation

Every node must be able to handle the largest block an attacker can build, not the average one. Lowering that worst case buys headroom, which can either be spent on throughput by raising the gas limit or kept as a buffer. Left unspent, it is a direct gain in robustness. [EIP-7623](./eip-7623.md) caps worst-case block size with a floor on calldata bytes, raised by [EIP-7976](./eip-7976.md) to 64 gas per byte. [EIP-7981](./eip-7981.md) extended that to access-list entries, and [EIP-8131](./eip-8131.md) generalises the floor to a uniform per-byte rule over all tx-content fields, including [EIP-7702](./eip-7702.md) authorization tuples and [EIP-4844](./eip-4844.md) blob versioned hashes. [EIP-7928](./eip-7928.md) introduces a new source of block bytes, the BAL, populated by runtime opcodes. None of those static floors cover it.

The cheapest BAL contributor is a cold `SLOAD`: 32 bytes for 2,100 gas. Combined with all-non-zero calldata, an attacker pushes intrinsic gas above the calldata floor, pays intrinsic, and gets calldata at 16 gas/byte while loading the rest of the block via `SLOAD` keys.

At a 60M gas limit:

| Attack | Worst-case block size |
|---|---|
| Pure calldata at floor | 0.894 MiB (target) |
| Auth-tuple bypass under EIP-8131 alone | 1.02 MiB |
| Cold-`SLOAD` bypass under EIP-7928 | **1.548 MiB** |

`SSTORE`, address access, `CREATE`, and successful EIP-7702 delegations give further vectors. This EIP closes them with one uniform mechanism.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

### Constants

```
FLOOR_GAS_PER_BYTE          = 64   # per-byte floor rate (EIP-7976)
BAL_BYTES_PER_ADDRESS       = 20
BAL_BYTES_PER_STORAGE_KEY   = 32
BAL_BYTES_PER_STORAGE_VALUE = 32
BAL_BYTES_PER_BALANCE       = 32
BAL_BYTES_PER_NONCE         = 8
DELEGATION_CODE_BYTES       = 23   # EIP-7702 delegation marker length
TX_MAX_GAS_LIMIT            = 2**24 # per-transaction execution gas cap (EIP-7825)
```

### Data meter and floor

Names such as `tx_env`, `set_delegation`, `generic_call`, and `set_code` refer to the execution-specs reference implementation.

Clients keep one per-transaction counter, `bal_data_bytes`, the bytes each opcode contributes to the BAL, and two per-transaction sets, `metered_addresses` and `metered_storage_keys`, the accounts and slots whose BAL entry has been metered. The transaction's floor is

```
floor = static_floor + bal_data_bytes * FLOOR_GAS_PER_BYTE
```

where `static_floor` is defined below and `bal_data_bytes` starts at zero. None of these is part of the signed transaction, RLP-encoded, gossiped, or persisted; no new transaction field or type is introduced. No gas is reserved or deducted from the execution budget; the floor is checked against `floor_limit` only to ensure the user can pay it if it ends up binding.

```
tx_env.floor_limit = min(tx.gas, TX_MAX_GAS_LIMIT)

def meter_bal_data(tx_env, num_bytes):
    floor = tx_env.static_floor + (tx_env.bal_data_bytes + num_bytes) * FLOOR_GAS_PER_BYTE
    if floor > tx_env.floor_limit:
        raise OutOfGasError
    tx_env.bal_data_bytes += num_bytes
```

`meter_bal_data` MUST be called before the matching BAL insertion or state mutation. A floor-side `OutOfGasError` MUST be handled exactly like an execution-gas out-of-gas in the same frame: the frame halts exceptionally, its remaining gas is consumed, its state changes are reverted, and the caller continues. `bal_data_bytes` keeps the value it had before the failed call, so no unpaid BAL byte ever exists. The floor binds the execution-gas dimension, of which a transaction may consume at most `TX_MAX_GAS_LIMIT` ([EIP-7825](./eip-7825.md)), so `floor_limit` caps it there as well as at `tx.gas`; transaction validation already holds the static floor to both bounds ([EIP-8037](./eip-8037.md)). The count is a deliberate upper bound on the transaction's actual BAL contribution (see [Reverts](#reverts) and [Repeated writes to the same slot](#repeated-writes-to-the-same-slot)); over-counting only raises the floor, never lowers it, so the bound below is never violated.

### Static floor seed

The tx-content portion of the floor (calldata, access-list entries, authorization tuples, blob versioned hashes) is defined by [EIP-8131](./eip-8131.md) as `tx_floor`. This EIP adds the per-auth BAL contribution that arises when an authorization is processed:

```
auth_bal_bytes = BAL_BYTES_PER_ADDRESS     #  20: authority address
               + DELEGATION_CODE_BYTES     #  23: delegation marker
               + BAL_BYTES_PER_NONCE       #   8: authority nonce

static_floor = tx_floor + FLOOR_GAS_PER_BYTE * auth_bal_bytes * num_authorizations
```

`tx_env.static_floor` holds this value. The per-auth term covers each authorization's worst-case BAL contribution statically, so `set_delegation` (which runs outside the EVM's exception handler) never meters at runtime.

Per-transaction accounting always adds BAL entries that no opcode places there: sender, coinbase, and target, each with address plus the relevant balance and nonce changes; the contract nonce on creation; the top-level EIP-7702 delegated target. These total at most 184 bytes. Together with the ~130 envelope bytes that EIP-8131 also charges to `TX_BASE`, they fit the `TX_BASE / FLOOR_GAS_PER_BYTE = 328` bytes of headroom in `TX_BASE`. Under [EIP-2780](./eip-2780.md) the floor base is `TX_BASE_COST = 12,000` for a self-transfer and 15,000 or more otherwise, 187 bytes of headroom or more: the implicit BAL entries still fit, but envelope included a bare transaction can exceed the headroom by up to ~55 bytes. That constant comes from EIP-2780's base cost, not from this EIP. The code a creation transaction deploys is not implicit and is metered at runtime like a `CREATE` deployment (below).

### Runtime data metering

Each trigger calls `meter_bal_data` with the byte count below, before the corresponding BAL entry is added:

| Trigger | Bytes added |
|---|---|
| First access to an account (`BALANCE`, `EXT*`, `CALL*` targets and the EIP-7702 delegation targets they resolve, `SELFDESTRUCT` beneficiary, `CREATE`/`CREATE2` deployed address) | 20 |
| First access to a storage slot (`SLOAD`, `SSTORE`) | 32 |
| `SSTORE` moving a slot off its pre-transaction value | +32 |
| `CALL` with non-zero value to a different account (caller's and recipient's balance) | 64 |
| `SELFDESTRUCT` with non-zero balance to a different beneficiary (both balances) | 64 |
| `CREATE` / `CREATE2` past the preflight checks (creating account's nonce) | 8 |
| `CREATE` / `CREATE2` after the collision check (new contract's nonce) | +8 |
| `CREATE` / `CREATE2` with non-zero endowment (both balances) | +64 |
| Successful deployment by `CREATE` / `CREATE2` or by a creation transaction, just before `set_code` | `len(deployed_code)` |

"First access" is the first time any opcode of the transaction touches the account or slot, tracked in `metered_addresses` and `metered_storage_keys`. The sets are never rolled back: [EIP-7928](./eip-7928.md) keeps an account or slot touched by a frame that later reverts, so touching it again after the revert adds no BAL entry. The frame's warm set is not the key: an entry the access list pre-warmed is not cold under [EIP-2929](./eip-2929.md) but still enters the BAL when first touched. A sender, recipient, coinbase, or precompile touched by an opcode is metered too, although `TX_BASE` already covers it; this only over-counts.

EIP-7928 records every account whose balance or nonce changes, so a value transfer and a creation meter both sides. The executing account's balance is metered on every such opcode although the BAL records one post-balance per account; this only over-counts. EIP-7702 delegations are covered by the static `auth_bal_bytes` term. `CALLCODE`, `DELEGATECALL`, and `STATICCALL` transfer no value out of the executing account and add no balance bytes.

The 32 storage-value bytes are metered by every `SSTORE` that moves a slot off its pre-transaction value — `original == current != new`, the same condition that charges the write cost — and are never given back. [EIP-7928](./eip-7928.md) records a single post-value per changed slot and demotes a slot whose post-value equals its pre-value to a no-op write in `storage_reads`, so a write that restores the value does remove the bytes from the BAL, but only if the frame it runs in commits; whether it will is unknown when the write executes. A refund taken inside a frame that then reverts would leave the change in the BAL with its bytes uncounted, breaking the bound. Metering without refunds keeps the count an upper bound at the cost of over-counting round trips (see [Repeated writes to the same slot](#repeated-writes-to-the-same-slot)).

### Final charge

```
tx.gasUsed = max(execution_gas_used, tx_env.static_floor + tx_env.bal_data_bytes * FLOOR_GAS_PER_BYTE)
```

Transaction validation continues to require `tx.gas >= max(intrinsic, static_floor)` and, under [EIP-8037](./eip-8037.md), `static_floor <= TX_MAX_GAS_LIMIT`.

### System transactions and withdrawals

System-contract calls ([EIP-2935](./eip-2935.md), [EIP-4788](./eip-4788.md), [EIP-7002](./eip-7002.md), [EIP-7251](./eip-7251.md)) and withdrawals do NOT consume from a per-transaction floor: they have no `floor_limit`, `meter_bal_data` MUST NOT halt them, and nothing is settled against a floor when they finish. Their BAL bytes are absorbed by the existing EIP-7928 block-level buffer `bal_items <= block_gas_limit / ITEM_COST`.

## Rationale

### Floor side, not intrinsic side

Raising opcode intrinsic costs would penalise every user, including ones who never bypass. Charging on the floor only bites when execution is too cheap to cover the floor, which is exactly the bypass case.

A pure intrinsic surcharge also fails to cap the block at `gas_limit / 64`: for any added per-`SLOAD` cost `X`, the optimum bypass still yields `B = gas_limit / 64 + 24 · gas_limit / (2100 + X)` bytes, with the residual only vanishing as `X` grows large. Floor-side charging gives a closed bound directly.

### Runtime extensions cannot make the floor bind on their own

Every runtime trigger pairs its `meter_bal_data` call with an execution charge larger than the floor extension itself:

| Trigger | Floor extension | Min execution charge |
|---|---:|---:|
| First account access (cold) | 1,280 | 2,600 |
| First `SLOAD` of a slot (cold) | 2,048 | 2,100 |
| `SSTORE` (cold, zero → non-zero) | 4,096 | 22,100 |
| `CALL` with non-zero value | 4,096 | 9,000 |
| `SELFDESTRUCT` with non-zero balance | 4,096 | 5,000 |
| `CREATE` / `CREATE2` (nonces only) | 1,024 | 32,000 |
| Deployed code (per byte) | 64 | 200 |

The charges are those in force when this EIP was drafted. [EIP-8038](./eip-8038.md) raises the account and storage charges; EIP-8037 moves the `SSTORE` set, `CREATE`, and code-deposit costs into state gas, leaving 12,100, 12,000, and `6 × ceil(len / 32)` gas in the execution dimension respectively, so every row but the last keeps the inequality and a deployment of `L` bytes becomes floor-bound in that dimension whenever `64 × L` exceeds the execution gas spent around it. That is the intended effect: the code is BAL bytes. A first touch of an entry the access list pre-warmed costs only 100 gas of execution, but the entry's intrinsic charges, 1,900 for a key under [EIP-2930](./eip-2930.md) and 2,048 under EIP-7981, exceed its 2,048 floor extension, so the inequality holds for it as well. For every other BAL-contributing opcode, `floor_extension < execution_gas`. Executing one more such opcode raises `execution_gas_used` by strictly more than it raises the floor. A transaction whose execution gas already exceeds its static floor therefore stays execution-dominated no matter how many BAL-contributing opcodes it runs: the gap between execution gas and floor can only widen. A floor-side `OutOfGasError` requires the floor to climb past `floor_limit`; from an execution-dominated state, execution-side OOG fires first.

The floor only binds when the static seed defined by [EIP-8131](./eip-8131.md) (calldata, access-list entries, auths, blob hashes) already pushes `static_floor` close to `floor_limit` before any opcode runs. That is precisely the calldata + cold-`SLOAD` bypass this EIP targets. Transactions whose static seed is small, the common case, cannot reach a binding floor through opcode execution alone. The one static seed that binds by itself is a skipped authorization; see [Backwards Compatibility](#backwards-compatibility).

### Capped by the execution-gas limit

[EIP-7825](./eip-7825.md) caps a transaction's execution gas at `TX_MAX_GAS_LIMIT`, and under [EIP-8037](./eip-8037.md), where `tx.gas` may exceed that cap to fund state gas, a block reserves only `min(tx.gas, TX_MAX_GAS_LIMIT)` of its execution-gas budget per transaction. Without EIP-8037, `tx.gas <= TX_MAX_GAS_LIMIT` already holds and `floor_limit = tx.gas`. The floor binds that dimension, so a floor above the cap would let a transaction's execution gas exceed its reservation and overflow the block gas limit. Capping the runtime floor at `floor_limit = min(tx.gas, TX_MAX_GAS_LIMIT)` mirrors the validation rule for the static floor and keeps block gas accounting sound.

### One per-byte rate

Pricing every BAL byte at the same `FLOOR_GAS_PER_BYTE` as non-zero calldata makes the worst case invariant to the attacker's choice: calldata, auths, storage keys, addresses, code, and balances all yield `1/64` bytes per gas at the floor. The optimum collapses to `B = gas_limit / 64`.

### Meter before; never refund

EIP-7928 keeps accessed addresses and storage keys in the BAL even when their call frame reverts. Metering each contribution before the insertion guarantees every BAL byte is accounted for, and an out-of-gas at the metering step aborts before the matching insertion. The meter is otherwise a deliberate upper bound, not an exact mirror of the BAL: changes from reverted frames are never rewound (see [Reverts](#reverts)), and no bytes are ever refunded, because either would entangle the meter with the existing revert and refund machinery for no benefit — the count feeds nothing but a floor that rarely binds, so over-counting is free.

The one candidate for a refund, a storage slot written back to its pre-transaction value, shows why refunds are unsafe. The slot's 32 value bytes do leave the BAL under EIP-7928, but only if the frame that performs the restoring write commits. A refund taken when the write executes, inside a frame that later reverts, leaves the earlier change in the BAL with its bytes uncounted, and the [block-size bound](#block-size-bound) no longer holds. Deferring the refund to the commit of every enclosing frame would be exact but costs the simplicity the meter is built on; counting the restoring write as nothing and keeping the earlier charge is both simpler and safe.

### First touch per transaction, not cold access

An access-listed storage key is priced as 32 content bytes by EIP-8131 and carries the 2,048 gas EIP-7981 surcharge in its intrinsic cost, but reading it adds another 32 BAL bytes that neither charge covers. A meter keyed on [EIP-2929](./eip-2929.md) cold accesses would never see them: the key is warm when read. Under the schedule in force when this EIP was drafted, the intrinsic charges happen to keep such a read at about 4,050 gas for 64 block bytes, just under the 64 gas per byte rate, but the bound would then rest on the EIP-2930 and EIP-7981 prices rather than on the meter. Metering the first touch per transaction charges the key's BAL bytes when, and only when, it is read: a listed key that is read carries `(32 + 32) × 64 = 4,096` floor gas, one that is never read only its 2,048 of content. Pricing every listed entry statically would be simpler but would charge entries that never reach the BAL. Per-transaction tracking has a second benefit: an account or slot touched inside a frame that reverts stays in the BAL and stays metered, and is not metered again when a surviving frame touches it, so the count is exact for keys and addresses.

### Per-auth coverage is static

`set_delegation` runs outside the EVM's exception handler. A runtime `meter_bal_data` raising `OutOfGasError` there would propagate uncaught and crash block processing. Folding the worst-case 51 BAL bytes per auth (on top of the 108-byte tuple priced by EIP-8131, for 159 B total) into the static floor lets `set_delegation` mutate state freely: any transaction whose `tx.gas` cannot cover it has already been rejected at validation.

### Counter, not a reservation

The runtime mechanism does not deduct gas from the execution budget or pre-commit any gas. `meter_bal_data` only increments `bal_data_bytes` and checks that the floor stays `≤ floor_limit`. Execution gas accounting is untouched. At the end, `tx.gasUsed = max(execution_gas_used, floor)`; the floor decides only how much of the upfront-debited `tx.gas × gas_price` gets kept versus refunded.

### `max(execution, floor)` preserved

The EIP-7623 / EIP-8131 charging shape is unchanged; only the floor side has a runtime tail. Transactions whose execution exceeds the floor pay exactly as today.

## Backwards Compatibility

Hard fork.

The static floor takes `tx_floor` from EIP-8131 and adds 51 BAL bytes per authorization; the runtime meter extends the floor for BAL bytes that opcodes contribute during execution. The combined floor per auth is `(108 + 51) × 64 = 10,176` gas. Under [EIP-2780](./eip-2780.md) an authorization's intrinsic share is `EXECUTION_PER_AUTH_BASE_COST = 7,816` gas, with the account-write and state charges taken only when the authorization is applied, so a type-4 transaction whose authorizations are all skipped (bad nonce, chain id, or signature) and that does nothing else pays the floor instead: 2,360 gas more per skipped authorization. Applied authorizations pay far more than their floor share. Otherwise the minimum `tx.gas` for a transaction only changes when the floor side already dominated, i.e. for calldata-heavy or BAL-heavy transactions. A bare ETH transfer stays at 21,000.

Mainnet sample (1,500 random blocks, 441,271 transactions, 20,000 of those traced for BAL bytes, May 2026): EIP-8131 alone makes 3.24% of transactions pay more (+3.29% gas). EIP-8279 adds another 0.54 pp and +0.77 pp, for a combined 3.79% / +4.06%. The runtime BAL piece never bites on its own: per-tx BAL bytes average 120-200 B after `TX_BASE` absorption, under 13 k floor gas, well below typical execution gas. Besides it, the floor binds by itself for a skipped authorization, by 2,360 gas as above, and under EIP-8037 for the code a deployment writes. EIP-8279's job is to close the calldata + cold-`SLOAD` bypass when paired with EIP-8131, not to add a standalone floor.

## Test Cases

Unless stated otherwise, the cases use the schedule in force when this EIP was drafted (`TX_BASE = 21,000`, `COLD_ACCOUNT_ACCESS = 2,600`, `TX_MAX_GAS_LIMIT = 2^24`); the skipped-authorization case uses [EIP-2780](./eip-2780.md) and EIP-8038 pricing.

### Bare ETH transfer

`tx.to = recipient`, `tx.value = 1 ether`, `tx.data = b""`.

- `static_floor = TX_BASE = 21,000` gas.
- Minimum `tx.gas = 21,000`, unchanged.

### Cold `SLOAD` bypass attempt

Pre-EIP block-level optimum at `block_gas_limit = 60M`: 937,500 non-zero calldata bytes plus 21,428 cold `SLOAD`s spread over the block's transactions, 1.548 MiB in all.

- Each cold `SLOAD` now extends its transaction's floor by `32 × 64 = 2,048` gas against 2,100 gas of execution.
- Every transaction's `gasUsed` is at least `64 ×` its block bytes, so the block holds at most `block_gas_limit / 64 = 937,500` bytes regardless of the calldata / `SLOAD` split.

A single transaction that hits the meter: `tx.gas = TX_MAX_GAS_LIMIT = 16,777,216` with 200,000 non-zero calldata bytes calling code that performs cold `SLOAD`s.

- Intrinsic: `21,000 + 16 × 200,000 = 3,221,000`; static floor: `21,000 + 64 × 200,000 = 12,821,000`.
- `(16,777,216 − 12,821,000) / 2,048 = 1,931.7`: the first 1,931 cold `SLOAD`s raise the floor to 16,775,688; the 1,932nd raises `OutOfGasError` inside `meter_bal_data`, although `16,777,216 − 3,221,000 − 1,931 × 2,100 ≈ 9.5M` execution gas remains.

### Cold `SSTORE` (zero → non-zero)

Single cold `SSTORE` writing a non-zero value to an empty slot.

- Metered: `32 (key) + 32 (value) = 64` BAL bytes → `4,096` gas added to the floor.
- Execution cost of the `SSTORE`: 22,100. `max(execution, floor) = execution`; the floor is dominated by execution gas.

### Net-zero `SSTORE` round-trip

Slot starts at original value `O`; the transaction writes `X ≠ O` then writes `O` again.

- First `SSTORE` (`O → X`): `32 (cold key) + 32 (value)` metered.
- Second `SSTORE` (`X → O`): the slot is back at its pre-transaction value, a no-op write under EIP-7928, but nothing is refunded.
- Net metered: `64`. The BAL records the slot in `storage_reads` only; the meter over-counts by 32 bytes and the bound holds.

### Restoring write in a reverting frame

Slot starts at `O`. The contract writes `O → X`, then `DELEGATECALL`s code that writes `X → O` and reverts.

- First `SSTORE`: `32 (cold key) + 32 (value)` metered; the `DELEGATECALL` meters `20` for the cold code address.
- The inner `SSTORE` meters nothing: the slot already differs from `O`. The revert restores `X`.
- Net metered: `84`, exactly the BAL's slot key, post-value `X`, and callee address. A refund on the inner write would have left `52`, under-counting the BAL.

### Access-listed storage key read warm

A transaction lists one storage key of its recipient in the access list and the recipient's code reads it with a single `SLOAD`.

- Intrinsic: `TX_BASE + 2,400 + 1,900 + 64 × (20 + 32) = 28,628`, the EIP-2930 charges plus the EIP-7981 surcharge; static floor: `TX_BASE + 64 × (20 + 32) = 24,328` for the listed address and key as content bytes.
- The `SLOAD` is warm (100 gas) but is the transaction's first touch of the slot, so it meters 32 bytes: the floor becomes `26,376`. A listed key that is never read meters nothing.
- `tx.gasUsed = max(28,728, 26,376) = 28,728`. The intrinsic side dominates here; the metered bytes count once calldata or further accesses push the floor past it. Keyed on cold access instead, the slot's 32 BAL bytes would never be metered.

### Skipped authorization

A type-4 transaction with one authorization whose nonce does not match, calling a contract that only `STOP`s, under EIP-2780 pricing.

- Intrinsic: `12,000 + 3,000 (recipient) + 7,816 (authorization base) = 22,816`; no `ACCOUNT_WRITE` or state-gas charge, since the authorization is skipped.
- Static floor: `12,000 + 3,000 + (108 + 51) × 64 = 25,176`.
- `tx.gasUsed = 25,176`: the floor binds, 2,360 gas above the intrinsic.

### Creation transaction deploying code

A creation transaction whose init code returns `N` bytes of code.

- Just before `set_code`, `N` bytes are metered: `64 × N` gas joins the floor, exactly as for a `CREATE` deployment.
- `floor_limit` must cover the floor plus `64 × N` at deposit time, including any bytes the init code metered, or the deployment halts with `OutOfGasError`, as it would for any other out-of-gas in init code.

### Repeated distinct writes

Slot starts at `O`; the transaction writes `A`, then `B`, then `C` (all distinct, `C ≠ O`).

- The `32` value bytes are metered once, on the `O → A` transition; `A → B` and `B → C` add nothing.
- Net metered: `32 (key) + 32 (value) = 64`, matching the single post-value `C` the BAL records.

### Reverted `CALL` with value

`CALL` with `value > 0` to a recipient that reverts.

- 20 address bytes for the recipient, on its first touch, and 64 balance bytes, the caller's and the recipient's, are metered before `generic_call`.
- Both balance changes are discarded on revert (per EIP-7928); the recipient stays in the BAL. Neither `bal_data_bytes` nor the floor is rewound.
- Over-accounting by 64 bytes; the bound still holds.

## Security Considerations

### Block-size bound

Per transaction, every byte the tx contributes to the block (tx blob + BAL) is accounted for at the floor rate via either the static seed or a runtime extension, with implicit per-tx bytes within the `TX_BASE` headroom (see [Static floor seed](#static-floor-seed)):

```
block_bytes_per_tx × FLOOR_GAS_PER_BYTE  ≤  floor  ≤  tx.gasUsed
```

Summing across user transactions:

```
sum(block_bytes) ≤ sum(tx.gasUsed) / 64 ≤ block_gas_limit / 64
```

System-contract and withdrawal contributions are bounded separately by the EIP-7928 block-level `ITEM_COST` buffer (~1,428 items at a 60M gas limit), sized to absorb existing system contract use.

### Reverts

Accessed addresses and storage keys persist in the BAL across reverts (per EIP-7928), and so do their entries in `metered_addresses` and `metered_storage_keys`; balance, nonce, code, and storage-value changes from reverted frames are discarded. Neither `bal_data_bytes` nor the floor is rewound for discarded entries, and no bytes are ever refunded, so a reverted frame can only leave the meter above the BAL, never below. Safe: the meter over-counts, never under-counts.

### Repeated writes to the same slot

The 32 storage-value bytes are metered by every `SSTORE` that moves a slot off its pre-transaction value. Repeated distinct writes (`A → B → C`) meter them once, matching the single post-value the BAL records per changed slot; a net-zero round-trip (`O → X → O`) meters them once while the BAL records no value, and `O → X → O → Y` meters them twice for the single post-value `Y`. `bal_data_bytes` over-counts in these cases, as it does for value bytes charged in a frame that later reverts; the bound holds.

### Gas estimation

Wallets and `eth_estimateGas` MUST compute the static floor, including the per-authorization term, and meter every trigger in the [runtime data metering](#runtime-data-metering) table when simulating execution. Without it, estimates for floor-bound transactions are too low: a transaction whose `tx.gas` is below its static floor is rejected at validation, and one whose runtime floor outgrows `floor_limit` is included and halts with `OutOfGasError`, paying for the gas it consumed.
