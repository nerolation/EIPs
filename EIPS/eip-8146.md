## Abstract

This EIP moves the block access list (BAL) introduced by [EIP-7928](./eip-7928.md) out of the `ExecutionPayload` and into a consensus-layer sidecar.

The builder adds the EIP-7928 `block_access_list_hash` to its signed `ExecutionPayloadBid`. This lets consensus clients authenticate the sidecar before the execution payload arrives. Consensus clients treat the BAL as opaque bytes and pass it to the execution layer immediately.

Payload timeliness now requires both an early BAL sidecar and a timely execution payload. No new Payload Timeliness Committee (PTC) vote is added.

## Motivation

In [EIP-7732](./eip-7732.md), the builder publishes the execution payload after the beacon block. EIP-7928 places the BAL inside that payload. The BAL therefore arrives on the same path as the data needed to execute the block.

A sidecar gives the execution layer the BAL first. It can prefetch the declared state and prepare state-root work while waiting for the payload. The payload message also becomes smaller.

At a 60 million block gas limit, the [1,000-block analysis](../assets/eip-7928/bal_size_analysis_60m.md) measured an average BAL size of 110.8 KiB raw and 72.4 KiB compressed, with observed maxima of 301.9 KiB raw and 191.4 KiB compressed.

FOCIL inclusion list committee members build their lists after processing the current slot's block, as specified by [EIP-7805](./eip-7805.md). An authenticated BAL can accelerate speculative prefetching and state-root work, but its post-values are not trusted until the execution payload is validated. Safe state updates and transaction filtering or simulation must wait for payload validation. Once validated, the earlier work can help members avoid selecting transactions invalidated by nonce or balance changes in the current block.

The BAL deadline is one second before the payload deadline. This creates a one-second CL receipt advance. Hashing, validation, and CL-to-EL delivery consume part of the execution layer's preparation window.

The BAL cannot be authenticated from `bid.block_hash` alone without reconstructing the execution header. Repeating the EIP-7928 `block_access_list_hash` in the signed bid makes early consensus-layer verification cheap. It does not define another hash.

## Specification

This specification is a delta against the Heze phase in `ethereum/consensus-specs` commit `2359a5e3444635ee2fc2acdea8a759e16391af90`. Its Engine API baseline is the Amsterdam and Bogota specifications in `ethereum/execution-apis` commit `742d45db810b31265c8d3c075af324953330d1ed`. It does not replace inherited definitions. `bytes32`, `uint64`, `uint256`, `boolean`, `Hash32`, `Root`, `Slot`, `ProgressiveByteList`, `ProgressiveContainer`, and `get_payload_due_ms` have the meanings used by those specifications.

`keccak256` means the legacy Keccak-256 function used by the execution layer, not SHA3-256.

### Consensus types

#### `BlockAccessList`

`BlockAccessList` remains the opaque, RLP-encoded byte string defined by EIP-7928:

```python
# [Inherited from EIP-7928]
class BlockAccessList(ProgressiveByteList):
    pass
```

This EIP does not add a second BAL size limit. The inherited `MAX_PAYLOAD_SIZE` networking limit is 10 MiB of uncompressed data per gossip message or RPC chunk. EIP-7928 remains responsible for execution-layer BAL validity and resource bounds.

#### Modified `ExecutionPayload`

The EIP-7928 `block_access_list` field is deactivated. The later `slot_number` field keeps its existing progressive-container index.

```python
# [Modified in this EIP]
class ExecutionPayload(ProgressiveContainer(active_fields=[1] * 17 + [0, 1])):
    parent_hash: Hash32
    fee_recipient: ExecutionAddress
    state_root: bytes32
    receipts_root: bytes32
    logs_bloom: LogsBloom
    prev_randao: bytes32
    block_number: uint64
    gas_limit: uint64
    gas_used: uint64
    timestamp: uint64
    extra_data: ExtraData
    base_fee_per_gas: uint256
    block_hash: Hash32
    transactions: Transactions
    withdrawals: Withdrawals
    blob_gas_used: uint64
    excess_blob_gas: uint64
    # [Deactivated in this EIP] Field index 17: block_access_list
    # [Inherited] Field index 18 remains active.
    slot_number: uint64
```

#### Modified `ExecutionPayloadBid`

A `block_access_list_hash` field is appended to `ExecutionPayloadBid`:

```python
# [Modified in this EIP]
class ExecutionPayloadBid(ProgressiveContainer(active_fields=[1] * 14)):
    parent_block_hash: Hash32
    parent_block_root: Root
    block_hash: Hash32
    prev_randao: bytes32
    fee_recipient: ExecutionAddress
    gas_limit: uint64
    builder_index: BuilderIndex
    slot: Slot
    value: Gwei
    execution_payment: Gwei
    blob_kzg_commitments: BlobKZGCommitments
    execution_requests_root: Root
    inclusion_list_bits: InclusionListBits
    # [New in this EIP]
    block_access_list_hash: Hash32
```

`bid.block_access_list_hash` MUST equal `keccak256(block_access_list)`, where `block_access_list` is the exact byte string returned by the execution layer for the payload committed by `bid.block_hash`.

The value MUST also equal the `block_access_list_hash` in the execution block header defined by EIP-7928.

#### `BlockAccessListSidecar`

```python
# [New in this EIP]
class BlockAccessListSidecar(Container):
    beacon_block_root: Root
    slot: Slot
    block_access_list: BlockAccessList
```

The sidecar has no signature. The builder signature on the bid authenticates `block_access_list_hash`. The beacon block identifies the selected bid.

This EIP does not assign a fork version or activation epoch. The fork that includes this EIP supplies both and incorporates these changes into its transition.

If the pre-fork `BeaconState` already contains the earlier `ExecutionPayloadBid`, the hosting fork MUST reconstruct `latest_execution_payload_bid` as follows while copying every other inherited state field. If the hosting fork introduces `ExecutionPayloadBid` at the same transition, it defines the new field directly and this migration is unnecessary.

```python
# [Conditional migration when upgrading an existing ExecutionPayloadBid]
post.latest_execution_payload_bid = ExecutionPayloadBid(

    fee_recipient=pre.latest_execution_payload_bid.fee_recipient,
    gas_limit=pre.latest_execution_payload_bid.gas_limit,

    execution_requests_root=pre.latest_execution_payload_bid.execution_requests_root,
    inclusion_list_bits=pre.latest_execution_payload_bid.inclusion_list_bits,
    # [New in this EIP]

```

### Builder behavior

When constructing a bid, the builder:

1. obtains the execution payload and BAL from the execution layer;
1. sets `bid.block_access_list_hash = keccak256(block_access_list)`;
1. signs and publishes the bid as specified by EIP-7732; and
1. keeps the exact BAL bytes used for the hash.

After seeing a valid beacon block that selects the bid, the builder SHOULD publish the corresponding `BlockAccessListSidecar` immediately. It SHOULD publish the sidecar before the `SignedExecutionPayloadEnvelope`.

### Sidecar validation

Let `block` be the validated beacon block whose root is `sidecar.beacon_block_root`, and let:

```python
bid = block.body.signed_execution_payload_bid.message
```

A sidecar is valid if:

```python
sidecar.slot == block.slot
keccak256(sidecar.block_access_list) == bid.block_access_list_hash
```

Consensus clients MUST NOT RLP-decode the BAL for this check.

After validation, the consensus client MUST pass the BAL and `bid.block_hash` to its execution layer without waiting for the execution payload.

A consensus client MUST NOT validate an execution payload for this beacon block until the matching BAL is available. If the payload arrives first, the client MUST queue it and process it when the BAL arrives.

### Payload timeliness

This EIP does not change `PayloadAttestationData`.

A PTC member sets `payload_present = True` only if both conditions hold:

1. a valid `BlockAccessListSidecar` was received before `get_block_access_list_due_ms()`; and
1. the matching `SignedExecutionPayloadEnvelope` was received before the payload deadline.

```python
BLOCK_ACCESS_LIST_ADVANCE_MS = uint64(1000)


def get_block_access_list_due_ms() -> uint64:
    assert get_payload_due_ms() > BLOCK_ACCESS_LIST_ADVANCE_MS
    return get_payload_due_ms() - BLOCK_ACCESS_LIST_ADVANCE_MS
```

A sidecar is timely if it is received before `get_block_access_list_due_ms()` milliseconds into the slot. The existing `payload_present` vote therefore covers both early BAL delivery and payload delivery. `blob_data_available` remains unchanged.

### Gossip

A new global gossip topic carries `BlockAccessListSidecar` objects:

```text
block_access_list_sidecar
```

The hosting fork MUST raise its type-specific `SignedExecutionPayloadBid` gossip bound from 196,934 bytes to 196,966 bytes.

Before forwarding a sidecar, a client applies these checks in order:

- _[IGNORE]_ The sidecar is not from a future slot. A client MAY queue it.
- _[IGNORE]_ The beacon block identified by `sidecar.beacon_block_root` is known. A client MAY queue the sidecar while retrieving the block.
- _[REJECT]_ The beacon block passes consensus validation.
- _[IGNORE]_ No valid sidecar for `sidecar.beacon_block_root` has already been accepted.
- _[IGNORE]_ `sidecar.slot` is not earlier than the first slot of the latest finalized epoch.
- _[REJECT]_ `sidecar.slot == block.slot`.
- _[REJECT]_ `keccak256(sidecar.block_access_list) == bid.block_access_list_hash`.

After these checks, the client records the beacon block root as seen and passes the sidecar to the sidecar handler.

### Req/Resp

Clients MUST support sidecar retrieval by range and by beacon block root. Each successful response chunk contains one `BlockAccessListSidecar`.

The protocol IDs are:

```
/eth2/beacon_chain/req/block_access_list_sidecars_by_range/1/
/eth2/beacon_chain/req/block_access_list_sidecars_by_root/1/
```

The range request contains:

```python
(
    start_slot: Slot,
    count: uint64,
)
```

The root request contains a list of at most `MAX_REQUEST_PAYLOADS` beacon block roots.

Range responses contain sidecars for blocks on the peer's canonical chain and are ordered by slot. A response contains at most one sidecar per requested slot or root and at most `MAX_REQUEST_PAYLOADS` sidecars in total.

Clients MUST retain every valid BAL sidecar they accept and serve retained sidecars for `MIN_EPOCHS_FOR_DATA_COLUMN_SIDECARS_REQUESTS` epochs. This reuses the existing sidecar retention window.

Each successful response chunk uses this EIP's `ForkDigest` context. Add the following mappings to the inherited response protocols:

| Protocols                                                                   | Chunk SSZ type                              |
| --------------------------------------------------------------------------- | ------------------------------------------- |
| `BeaconBlocksByRange` v2, `BeaconBlocksByRoot` v2                           | This EIP's `SignedBeaconBlock`              |
| `ExecutionPayloadEnvelopesByRange` v1, `ExecutionPayloadEnvelopesByRoot` v1 | This EIP's `SignedExecutionPayloadEnvelope` |

For the two BAL sidecar protocols, each successful response chunk contains one `BlockAccessListSidecar` from this EIP. Derive its `ForkDigest` context epoch from `sidecar.slot`.

### Engine API

The Engine API separates BAL delivery from payload delivery.

#### `ExecutionPayloadV5`

`ExecutionPayloadV5` has the same fields as `ExecutionPayloadV4`, except that `blockAccessList` is removed. `slotNumber` remains the final field.

`engine_forkchoiceUpdatedV5` and `PayloadAttributesV5` are unchanged. The method remains valid after activation and starts the payload build whose `payloadId` is consumed by `engine_getPayloadV7`.

#### `engine_getPayloadV7`

This method follows `engine_getPayloadV6` from the Amsterdam baseline above, but returns `ExecutionPayloadV5`. Its result adds:

- `blockAccessList`: `DATA` - the exact RLP-encoded BAL bytes.

The new field is a sibling of `executionPayload`.

The execution layer MUST return `-38005: Unsupported fork` if the built payload's timestamp is before this EIP's activation.

#### `engine_newBlockAccessListV1`

This method delivers a BAL before its payload.

- method: `engine_newBlockAccessListV1`
- params:
  1. `blockHash`: `DATA`, 32 bytes - the execution block hash committed by the selected bid;
  1. `blockAccessList`: `DATA` - the RLP-encoded BAL bytes.
- result: `null` after the BAL has been accepted and stored;
- timeout: 1 second.

The execution layer MUST return `-32602: Invalid params` if either parameter is malformed. On success, it stores the BAL by `blockHash`. Repeating the same call MUST succeed. A different BAL for an existing `blockHash` MUST return `-32602: Invalid params`.

The execution layer MAY discard this cached BAL at any time. This does not affect payload validity because `engine_newPayloadV7` receives the BAL again. The execution layer MAY begin state prefetching or state-root work immediately. An error or timeout from this prefetch call MUST NOT invalidate the sidecar or prevent later payload processing. The consensus layer MAY retry the call.

#### `engine_newPayloadV7`

This method follows `engine_newPayloadV6` from the Bogota baseline above, but:

1. replaces its `executionPayload` parameter with `ExecutionPayloadV5`; and
1. appends `blockAccessList`, containing the exact RLP-encoded BAL bytes.

All other parameters, including `inclusionListTransactions`, are unchanged. The BAL supplied here is authoritative for validation. A BAL cached by `engine_newBlockAccessListV1` is only a prefetch hint.

All EIP-7928 checks still apply. In particular, the execution layer MUST:

1. compute the execution header's `block_access_list_hash` from the received BAL;
1. verify the execution block hash; and
1. execute the block and verify that the generated BAL equals the received BAL.

The execution layer MUST return `-38005: Unsupported fork` if the payload's timestamp is before this EIP's activation.

After this EIP activates, `engine_getPayloadV6` and `engine_newPayloadV6` MUST return `-38005: Unsupported fork` for payloads at or after the activation timestamp.

### Execution layer

EIP-7928 BAL construction, ordering, validity, and block-header rules are unchanged.

## Rationale

### Reuse the execution-layer hash

The bid repeats the same Keccak-256 value already present in the execution header. A new SSZ commitment would make the two layers reconcile two hashes for the same bytes.

The repeated field is needed because the CL cannot recover an execution-header field from `bid.block_hash` before receiving the payload.

### Reuse `payload_present`

The BAL is required to validate the payload. Treating early BAL delivery as part of payload timeliness avoids another PTC bit, another vote tracker, and more fork-choice rules. A late BAL therefore has the same payment effect as a late payload. This is intentional: the builder's timely delivery obligation covers the complete execution-validation bundle.

### No sidecar signature

The selected bid is signed by the builder and included in a signed beacon block. Matching the sidecar against `bid.block_access_list_hash` authenticates it. A second signature adds no useful binding.

### Early publication

The BAL contains no signed transactions and cannot be submitted as an alternative payload. Publishing it before the payload therefore does not expose an executable transaction bundle. It does reveal the block's state footprint, which is the information needed for prefetching.

### Keep the CL opaque

The CL only hashes bytes. BAL decoding and semantic validation stay in the EL, where EIP-7928 is implemented.

## Backwards Compatibility

This EIP requires a hard fork. It changes `ExecutionPayload`, `ExecutionPayloadBid`, payload timeliness, consensus networking, and the Engine API.

## Security Considerations

A builder can withhold the sidecar. PTC members then set `payload_present = False`, and the existing EIP-7732 payload-withholding path applies.

A builder can publish malformed BAL bytes whose hash matches the bid. The CL accepts the sidecar as available, but the EL rejects the payload under EIP-7928. This is the same separation used for execution payload validity: the CL authenticates bytes, while the EL checks execution semantics.

The bid contains both `block_hash` and `block_access_list_hash`. If these commitments are inconsistent, reconstructing and validating the execution block hash fails.

Sidecar hashing is linear in the BAL size. Existing consensus networking message-size limits bound the work performed before forwarding.

This EIP moves the BAL bytes from the execution-payload-envelope topic to the sidecar topic rather than duplicating them in consensus gossip. Total gossip load is therefore approximately unchanged, apart from sidecar framing and the 32-byte bid commitment. The separate topic changes per-topic traffic shape and peer scheduling, so implementations SHOULD apply the same bandwidth controls used for other bounded sidecar topics.
